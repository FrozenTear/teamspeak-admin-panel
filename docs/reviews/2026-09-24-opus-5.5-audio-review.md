# Opus 5.5 review: music-bot audio lag and underruns (#70)

Date: 2026-09-24. Scope: the audio path end to end (decode, Opus encode,
pacing, connected loop, vendored tsclientlib/tsproto send path and acks,
voice-rt / decode-rt runtimes, hot-path logging, mute and talk-power
state, Contabo deploy config). Documentation only. No code, config, or
server was changed for this review.

Inputs: the three attached music-container logs (v1.6.22 and v1.6.21
clean Angerfist A/B from today, Sep 16 post-pin Angerfist reference),
issues #70, #40, #44, and the repo at `main` (`105b514`). Every count
below was recomputed from the raw JSON logs; the method is in the
appendix so the owner can rerun it.

## TL;DR

1. **The #70 signature is a whole-runtime stall of the voice runtime,
   not one slow arm.** On both of today's runs about 800 send gaps of
   100 ms or more add up to about 150 s of a 10.5-minute play. Only 30% of
   that time is covered by an instrumented `connected_loop_stall` or
   `voice_poll_leg` freeze, and 61 to 63% once the pacer sibling's own
   lateness is added. The pacer task and the connected loop stall
   together, which points at the voice-rt threads not getting CPU on
   cores 0-1.
2. **The instruments that were read as "no CPU shortage" cannot see CPU
   shortage on the send threads.** `proc_runqueue_wait_ms` reads
   `/proc/self/schedstat`, which only covers the main thread, not the
   voice-rt threads. `host_steal_ms` is 0 in every window of all three
   logs, including Sep 16 when the runqueue figure was in the hundreds of
   ms. Lead 2 ("tokio worker contention, not CPU") is not supported.
3. **Today is not 2x worse on the audible metric.** Real `frame_underrun`
   events are 139 to 161 per minute today against 146 per minute on
   Sep 16. Total rising-edge lateness is 8.4 to 9.1 s/min against
   8.0 s/min. The "266 underruns/min" figure is a `grep -c underrun`
   line count, and every `connected_loop_stall` line also matches it
   because its message text says "frame_underrun". What did roughly
   double against Sep 16 is on the connected-loop side, per minute:
   loop-stall milliseconds (1.9x), C_loop attribution lines (1.9x),
   poll-leg freeze time (1.6 to 1.7x), and `send_audio` calls of 10 ms
   or more (6.2 to 6.8x).
4. **The "Sending audio while muted" WARN fires on exactly every frame**
   (50.00 per second on both runs, starting at frame 1). It is emitted
   inside `con.send_audio`, and it is the only in-process difference on
   the send path between Sep 16 and today. The vendored tsclientlib and
   tsproto are byte-identical from v1.6.13 to v1.6.22. Its direct cost is
   about 10 to 25 µs per frame. It is a plausible amplifier of the
   loop-side regression but cannot explain the #70 signature, which
   #40, #44 and the Sep 16 log show without it.
5. **Audible audio plus a WARN on every frame means the bot's book
   disagrees with the server.** On TS6 the only server-side voice
   suppression this repo knows of is the talker flag in a moderated
   channel (`webquery/mod.rs:755-770`), and that is all-or-nothing. A
   one-shot read-only `clientinfo` plus `channelinfo` for bot 7 on Floki
   will show which predicate fails.

Recommended order of experiments (cheapest and most decisive first):
the E1 CPU census of cores 0-1 during a play, E2 the `RUST_LOG`-only
A/B, E3 moving the ack-sender thread off 0-1, E4 the split wire task,
and E5 the `clientinfo`/`channelinfo` read. All five are described
below with pass/fail criteria.

### 1.2 How the brief's per-minute figures were derived

The brief's figures reproduce exactly as grep line counts divided by
play minutes:

- "underrun" = `grep -c underrun`: 2,808 / 10.56 = 266 and
  2,458 / 10.68 = 230. That is `frame_underrun` plus every
  `connected_loop_stall` line, whose message ends "correlate with a
  mid-song frame_underrun" (`crates/voice/src/bot.rs:334-337`). On Sep 16
  the same grep gives 216/min.
- "C_loop" = attribution lines with `dominant=C_loop_deferral`.
- "stall" = `connected_loop_stall` lines.
- "55% on a full buffer" = 1,543 / 2,808. Against real underrun events
  the figure is 91 to 93% today and 97% on Sep 16.

Two further caveats about these counters:

- **One stall produces many attribution lines.** The sibling-to-loop
  channel is 32 frames deep (`crates/voice/src/audio.rs:50`). After a
  stall the loop drains the backlog back to back, and every drained frame
  gets its own attribution WARN with nearly the same
  `c_loop_deferral_us`. At 08:30:11.232 on v1.6.22, for example, 20
  attribution lines land within 1 ms. The C_loop count therefore measures
  queue depth times stalls, not the number of stalls.
- **`frame_underrun` only sees pacer lateness.** Lateness is sampled
  when the sibling pops a PCM frame (`audio.rs:985-1002`), before it
  hands the Opus frame to the loop. A connected-loop stall shorter than
  the 32-frame channel (640 ms) does not make the sibling late, so it
  never shows up as an underrun, even though the frame reaches the wire
  late. The attribution and stall counters see those stalls; the
  underrun counter does not.

## 2. Ranked root-cause hypotheses

### H1 (highest). The voice-rt threads on SEND cores 0-1 lose the CPU for tens to hundreds of ms

**Claim.** The dominant cause of #70 on every build since the soft pin
is OS-level starvation of the voice runtime threads on cores 0-1. The
cause is either other runnable work on those cores, or CPU time taken
from the vCPU without being reported as steal. Tokio scheduling inside
the voice runtime is not the main factor.

**Evidence.**

- The stalls are runtime-wide. In 61 to 63% of the long send-gap time
  the pacer sibling and the connected loop are both late at once. They
  are separate tokio tasks, and the sibling does almost nothing (a timer
  sleep and a ~100 µs encode, `audio.rs:1039`, `audio.rs:1068-1070`).
- The pacer oversleeps by up to 445 ms (v1.6.22) and 632 ms (v1.6.21).
  The voice runtime has 4 workers (`crates/voice/src/runtime.rs:51`) and
  about three per-bot tasks. A timer that fires 400 ms late with 4
  workers and 3 tasks needs every voice-rt thread to be off the CPU or
  stuck, not just queued.
- 236 of 331 (v1.6.22) and 202 of 281 (v1.6.21) poll-leg freezes are
  mostly off-CPU. `send_acks` is the top leg in 266 and 243 of them, and
  that leg does only a `to_vec` and a lock-free channel push per packet
  (`vendor/tsclientlib/tsproto/src/connection.rs:320-335`).
- Six poll-leg freezes happen on v1.6.21 **before the first frame**,
  while only the resolver was busy. The worst is 248 ms, of which
  247.9 ms is off-CPU. The warm resolver runs pinned to 2-5
  (`crates/music-bot-audio/src/resolver.rs:795`). Nothing was playing,
  so voice-rt load was near zero; the send cores themselves were busy.
- The brief's run "with other load on the box" (v1.6.22, 799 C_loop/min)
  and v1.6.15 before the soft pin (590 C_loop/min) show that the same
  code swings about 2.7x with host load and layout alone.
- The instruments that seemed to rule this out are blind here:
  - `proc_runqueue_wait_ms` reads field 2 of `/proc/self/schedstat`
    (`audio.rs:716-719`). That file is the thread-group leader's
    statistics only. The music binary's main thread is parked in
    `#[tokio::main]` (`crates/voice/src/bin/ts6-manager-music.rs:57`).
    The voice-rt threads are in `/proc/self/task/<tid>/schedstat` and
    are never read. On Sep 16 the bot lived inside the fullstack process,
    whose main thread did real work, which is why that log shows
    hundreds of ms.
  - `host_steal_ms` is 0 in all 64 `pacer_wakeup` windows across the
    three logs. That either means no steal, or a guest that does not get
    a steal clock from the hypervisor. In the second case, stolen time
    (and, without `CONFIG_IRQ_TIME_ACCOUNTING`, softirq time) is charged
    to whichever thread was running. That would also explain why
    today's long `send_audio` calls look "on-CPU" (median CPU/wall of
    0.66 to 0.89 for `t_send >= 10 ms`) although the call does
    microseconds of work.
- Nothing fences cores 0-1 for the send threads. Only fullstack is pinned
  (2-5, `deploy/contabo/soft-pin.env`), and so are the voice-rt and
  decode-rt threads inside music. The sidecar is explicitly unpinned.
  The music process's own `#[tokio::main]` runtime (6 workers by
  default, Axum control plane) is unpinned. conmon, journald, sshd,
  podman, and NIC softirq (`hostNetwork: true`) are unpinned. When 2-5
  are busy with fullstack at nice -5 plus ffmpeg and yt-dlp, the load
  balancer's only place for that work is 0-1.

**Fix proposal.**

1. Fence 0-1 for the send threads. Move everything else off them:
   `AllowedCPUs=2-5` on `system.slice` and the podman user slice (with a
   carve-out for the music voice-rt threads), sidecar cpuset 2-5, pin the
   music main runtime to 2-5 in `main()`, and steer NIC IRQs to 2-5 via
   `/proc/irq/*/smp_affinity`. Alternatively, give SEND one dedicated
   core with a `current_thread` wire runtime and move everything else off
   it.
2. Fix the instruments so the next A/B can see this. Sum `run_delay`
   (field 2) from `/proc/self/task/<tid>/schedstat` over the voice-rt,
   blocking-pool and `tsproto-ack-sender` tids in `pacer_wakeup`. Add a
   per-window `nr_involuntary_switches` delta for the same tids.

**Expected effect.** If H1 holds, fencing should remove most of the
runtime-wide gaps: the `voice_poll_leg` off-CPU freezes, pacer
oversleep above 20 ms, and the unattributed gap time. It should cut
underruns on both baselines and today, not only today's excess.

**Cheapest decisive experiment (E1).** Zero code. During one Angerfist
play, on the host:

- Snapshot `/proc/<music pid>/task/*/schedstat` and `comm` at play start
  and end. Sum the `run_delay` deltas for `voice-rt` and
  `tsproto-ack-sender` tids.
- Run `mpstat -P 0,1 1` and `pidstat -t -u 1` for the whole play, and
  sample `ps -eLo psr,ni,pcpu,comm --sort=-pcpu | awk '$1<=1'` every
  few seconds.
- Read `grep '^cpu ' /proc/stat` twice, 60 s apart, under load. Check
  `dmesg | grep -i steal` and whether the steal column ever moves.

Pass: voice-rt `run_delay` over the play is in the tens of seconds, and
there are identifiable non-music tasks on 0-1, or 0-1 show high
`%soft`/`%irq`. Fail: `run_delay` is under about 1 s across all voice-rt
tids while the gaps persist. That would move weight to H3 and H4.

### H2. The per-frame muted WARN amplifies the connected-loop side

**Claim.** The "Sending audio while muted" WARN fires on every frame
inside `con.send_audio`, and that `send_audio` call runs inside
`block_in_place` in the connected loop's audio arm. It is a plausible
contributor to today's loop-side excess over Sep 16. It is not the root
cause of the #70 signature.

**Evidence for.**

- It fires on exactly every frame: 50.00/s on both runs, from frame 1
  (08:21:17.521) to the end. The count is flat across v1.6.21 and
  v1.6.22.
- It sits on the hot path: `lib.rs:945-948` inside `send_audio`, called
  from `send_opus_frame` (`audio.rs:1385-1395`) with `block_in_place` on
  the single-loop path (`bot.rs:688-689`). The event is formatted as
  JSON and written synchronously to stdout (`ts6-manager-music.rs:65-79`,
  default `fmt` writer, no non-blocking appender in the workspace).
- The vendored send path is unchanged since Sep 16
  (`git diff v1.6.13 v1.6.22 -- vendor` is empty), and so are the
  send-path constants. So the WARN is the only new work inside
  `send_audio`. The count of `send_audio` calls of 10 ms or more went
  from 82 (4.7 s) on Sep 16 to 491 to 533 (27 to 30 s) today.
- It is 77% of today's log volume (31.7k of 41.1k lines). The rate is
  about 65 lines/s against 8.7 lines/s on Sep 16, so about 50 more
  `write(2)` calls and conmon wakeups per second, all issued from a
  send-core thread.

**Evidence against it being the main cause.**

- The audible metric is flat: `frame_underrun` is 139 to 161/min today
  against 146/min on Sep 16 without any WARN. #40 (v1.6.12) and #44
  (v1.6.13) show the same full-buffer C_loop signature before the WARN.
- The direct in-process cost is small. In drain bursts, about 20 frames
  each log a muted WARN and an attribution WARN within about 1 ms. That
  puts the full format-and-write path at about 10 to 25 µs per line.
- Stdout lock contention is rare. Lines whose timestamp is 20 ms or more
  older than a line already written (events that waited for the stdout
  lock or were preempted between format and write): 43 on v1.6.22, 38 on
  v1.6.21, 18 on Sep 16. If the pipe were blocking, this would be
  thousands.

**Fix proposal.** Zero-code mitigation: set
`RUST_LOG=info,music_bot=info,music_bot_audio=info,music_bot_latency=info,tsclientlib=error`
in the music container env. Note that the kube manifest sets
`LOG_LEVEL=info` (`deploy/kube/ts6-manager.yaml:192-193`), but the
music binary only reads `RUST_LOG` (`ts6-manager-music.rs:65`), so
`LOG_LEVEL` has no effect there. This also hides tsclientlib's other
WARNs (for example "Connection got a non-fatal error"), so treat it as
an experiment setting. The durable fix (in a later PR) is a vendored
patch that logs the mute state once per `CanSendAudio` transition,
which tsclientlib already tracks (`lib.rs:694`, `lib.rs:785`,
`lib.rs:1156-1158`), plus fixing the state itself (section 4).

**Expected effect.** Removes about 77% of log volume and about 50
syscalls/s from the send cores. If H2 matters, `t_send >= 10 ms` should
fall toward the Sep 16 level (about 80 per 10 minutes), and loop-stall
ms toward about 40 s per 10 minutes. I expect little change in
`frame_underrun`.

**Cheapest decisive experiment (E2).** Rerun the same clean Angerfist
A/B on v1.6.22 with only the `RUST_LOG` change. The muted WARN is then
gone, and with it the per-frame send trace, so compare `t_send >= 10 ms`
count and sum, loop-stall ms, `c_loop_deferral_us` p50/p99, poll-leg
freeze time, and `frame_underrun` per minute. Pass (H2 material):
`t_send >= 10 ms` drops by 3x or more and loop-stall ms by 30% or more.
Fail: both within about 15% of today. Running E1 in the same session
separates H1 from H2 cleanly.

### H3. The send design turns every short stall into a gap plus a burst, and churns threads

**Claim.** Three properties of the single-loop send path amplify any
H1 or H2 stall.

1. `send_audio` does not send. It pushes the voice packet onto
   `acks_to_send` (`connection.rs:450-470`). The packet only leaves when
   the event arm next polls `Connection::poll_next`, which flushes via
   `poll_send_acks` (`connection.rs:615-637`). The select is `biased`
   with audio first (`bot.rs:393-427`), so after a stall the loop drains
   up to 32 queued frames back to back before it polls events once. The
   whole backlog then goes out as a single burst. That explains the
   30 to 31% back-to-back sends.
2. Every frame goes through `block_in_place` (`bot.rs:688-689`,
   `audio.rs:1391-1392`). On a multi-thread runtime that hands the
   worker core to a blocking-pool thread, so each frame costs at least
   one cross-thread handoff on two contended cores. Afterwards the loop
   task can end up on the inject queue. In stalled arms the
   `t_blockinplace - t_send` churn sums to 14.2 s (v1.6.22), 10.4 s
   (v1.6.21) and 10.7 s (Sep 16).
3. The voice-rt pool growth (lead 5) comes from this. The 4 workers
   start at process boot (`ensure_voice_runtime`, before these logs
   begin), so every `on_thread_start` line in the logs is a new
   blocking-pool thread: 37 on v1.6.22 and 27 on v1.6.21. They arrive in bursts of 10 to 19 within one
   second: 08:21:17, 08:22:13, 08:30:13 on v1.6.22, and 08:38:16 on
   v1.6.21. Each burst coincides with a severe stall cluster, such as
   the 818 ms deferral at 08:22:11.9. In tokio 1.52.3 the blocking pool
   holds up to 512 threads with a 10 s keep-alive. When the handoff
   threads cannot get CPU, `block_in_place` finds no idle thread and
   spawns a new one. Idle threads exit after 10 s and are respawned at
   the next cluster. This is expected tokio behaviour, not a leak. It
   does add more runnable nice -5 threads to cores 0-1 at the worst
   possible moment, and each new thread runs `setpriority` and
   `sched_setaffinity` and logs two lines (`runtime.rs:69-97`).

**Fix proposal.** First, enable the split wire task that already exists
(`VOICE_SPLIT_WIRE_TASK=1`, `bot.rs:93`, `bot.rs:562-575`). It drops
`block_in_place` (`bot.rs:761`) and bounds every wire-task arm to one
cheap operation. It has never been A/B'd on Contabo according to docs
and deploy config. Later, in code: flush voice packets right after
enqueue (call the ack flush from the audio arm, or have the wire task
poll the connection once per frame), and decide on a stale-frame
policy. Dropping frames that are already past a lateness budget is
usually better for listeners than bursting 32 frames into the jitter
buffer.

**Expected effect.** Removes the A churn (10 to 14 s of stalled-arm time
per 10 minutes) and the pool growth, and should cut back-to-back sends
sharply. It does not remove H1 stalls, but shortens their audible tail.

**Cheapest decisive experiment (E4).** A/B with `VOICE_SPLIT_WIRE_TASK=1`
in the music env on v1.6.22, same track, same bot. Pass: no new
`pinned current thread` lines after play start, A-churn near 0, and
back-to-back send share below 10% (needs the WARN trace, so run it
before E2 or together with it). Fail: stall and gap totals unchanged,
which would point back to H1.

### H4. The ack-sender thread shares the send cores and is woken for every flush

**Claim.** `tsproto-ack-sender` is spawned from a voice-rt thread at
connect time (`connection.rs:217-231`), so it inherits the 0-1 affinity
and the nice -5 of that thread. Every flush (about 50/s, plus the
bursts) calls crossbeam `try_send`, which unparks it when it is idle,
which is almost always. That is a same-core wakeup of an equal-priority
thread, and that thread then competes with the loop for the same two
cores. It matches the dominant freeze shape: `send_acks` on top and
mostly off-CPU (266 of 331 and 243 of 281 on top; those freezes carry
9.0 s and 9.2 s of off-CPU time).

**Fix proposal.** Pin the ack-sender off 0-1, or send voice inline with
a non-blocking `send_to`. A non-blocking UDP send is a few µs. The
PURA-403 finding that the inline send took 8 to 57 ms with wall roughly
equal to CPU may itself have been hidden steal or softirq time (see H1).

**Expected effect.** Fewer and shorter `voice_poll_leg` freezes with
`send_acks` on top. If the freezes stay the same size, H1 is the driver
and this is cosmetic.

**Cheapest decisive experiment (E3).** Zero code:
`taskset -pc 2-5 <tid of tsproto-ack-sender>` on the live bot 7
process mid-play, and compare the `voice_poll_leg` rate and
`send_acks_us` in the 5 minutes before and after. Pass: `send_acks` top
freezes drop by half or more.

### H5. Measurement artifacts inflate the headline and hide the real gap

Not a cause, but it changes how the data should be read (section 1.2).
The grep "underrun" figure double-counts stalls. The C_loop figure
scales with queue depth. `frame_underrun` misses loop stalls under
640 ms, and runqueue and steal are blind to the send threads.

**Fix proposal.** In a later instrumentation PR:

- Define underruns as `frame_underrun` events only.
- Add a per-window `send_gap_ms_ge_100` counter and a
  `max_send_gap_ms` to `audio_send_summary`, measured in
  `send_opus_frame`. That gives the per-frame trace without the WARN.
- Report attributions per drain burst rather than per frame.
- Adopt the per-tid schedstat change from H1.

**Expected effect.** Comparable numbers across runs. **Experiment:** none
needed. Rerun the appendix commands on any future log.

### H6 (low). Background churn on voice-rt from bot 1's handshake loop

Bot 1 retries a handshake to `127.0.0.1:9987` every 66 s (10 attempts
per run, `attempt=30`, 5 Init resends each). That accounts for all 49
`tsproto::resend` lines in each log. It runs on voice-rt and spawns a
connection (and an ack-sender thread) on each attempt. The cost is
small. The same data shows bot 7's own connection had **zero** command
resends, so there is no sign of packet loss on the Floki link.

**Fix proposal.** Disable bot 1 or cap its retries with a longer
backoff. **Expected effect:** marginal. **Experiment:** none needed
beyond removing the noise before the next A/B.

## 3. Why today is about 2x worse than Sep 16/18

**Short answer.** On the metrics closest to what listeners hear
(underrun events and lateness), today is between 10% better and 14%
worse than Sep 16. On connected-loop metrics it is about 1.6 to 1.9x
worse. The data narrows the cause to host CPU availability on 0-1 and
the per-frame WARN, but cannot separate those two without E1 and E2.

**What the numbers say.**

| Ratio today / Sep 16 | v1.6.22 | v1.6.21 |
| --- | --- | --- |
| `frame_underrun` per min | 1.10 | 0.95 |
| Full-buffer underruns per min | 1.03 | 0.90 |
| Lateness sum per min | 1.14 | 1.05 |
| C_loop attribution lines per min | 1.87 | 1.87 |
| Loop-stall ms per min | 1.92 | 1.86 |
| Poll-leg freeze time per min | 1.72 | 1.60 |
| `send_audio >= 10 ms` count per min | 6.8 | 6.2 |

**What differs between Sep 16 and today.**

1. **Topology.** The Sep 16 log (23:37Z on Sep 15) is v1.6.13, which has
   no `ts6-manager-music` binary. That arrived with #47 on Sep 18. On
   Sep 16 the bot ran inside the fullstack process on cpuset 2-5 (four
   cores, shared with Axum and Surreal). Today the send threads are

## 4. Talk power, mute state, and the "Sending audio while muted" path

### 4.1 What tsclientlib checks

`Connection::send_audio` (`vendor/tsclientlib/tsclientlib/src/lib.rs:939-954`)
calls `intern_can_send_audio` (`lib.rs:1042-1066`). If that returns false
it logs the WARN and **sends the packet anyway** (`lib.rs:949`). The
check reads the bot's own client from the server-fed book:

- It returns false if `input_muted`, `!input_hardware_enabled`,
  `away_message.is_some()`, `output_muted`, or `!output_hardware_enabled`.
- If the bot's channel has `needed_talk_power` set, it returns
  `talk_power_granted || talk_power >= needed_talk_power`. `ChannelList`
  always carries `channel_needed_talk_power`
  (`vendor/tsclientlib/utils/tsproto-structs/declarations/Messages.toml:450`),
  so this branch is live for every channel. With `needed_talk_power = 0`
  it passes unless the book's `talk_power` is negative.
- If the own client is not in the book yet, it falls back to
  `ConnectOptions`. The bot uses defaults there
  (`crates/voice/src/bot.rs:1492-1499`): unmuted, hardware on, not away
  (`lib.rs:386-390`). The bot never sends `clientupdate`.

The book is populated from `notifycliententerview` (all five flags,
`client_talk_power`, `client_is_talker`) and later
`notifyclientupdated`. `ClientMoved`, `ClientServerGroupAdded` and
`ClientChannelGroupChanged` do not touch `talk_power`
(`declarations/MessagesToBook.toml:120-205`). If talk power changes
through a group change after the bot enters view, the book stays stale
unless the server also sends `client_talk_power` in
`notifyclientupdated`.

The bot never surfaces tsclientlib's `AudioEvent::CanSendAudio` items.
They fall into the `"other"` bucket (`bot.rs:359-367`). So the logs say
the predicate is false but not which field made it false.

### 4.2 What the TS6 server enforces

The repo's own TS6 notes (`crates/ts6-manager-server/src/webquery/mod.rs:755-770`,
`docs/flows/automod.md:159-171`) say:

- Server-side voice suppression on TS6 6.0 is the **talker flag in a
  moderated channel** (`channel_needed_talk_power > 0`). In an
  unmoderated channel every client may speak regardless of the flag, and
  TS6 rejects `client_is_talker=1` there with error 1538.
- `client_input_muted` and `client_output_muted` are client-self state.
  TS6 rejects them on `clientedit` for any other client, so the panel's
  "mute" is really `client_is_talker=0` (`routes/control/clients.rs:185-205`).
  These flags, and the hardware and away flags, are status the client
  reports. Nothing in the repo or the TS3-family protocol suggests the
  server drops voice because of them.

Voice packets are unacknowledged, so the bot cannot see whether the
server forwards them. The only suppression mechanism known here is
all-or-nothing per client state. There is no known per-packet voice
throttle. Since audio is audible for the whole play, the server treats
bot 7 as allowed to speak, and the book view that trips the WARN
disagrees with the server's view. Put simply, the server is not dropping
or throttling because of the condition the WARN reports. Any partial
loss would have a different cause (for example the gaps and bursts in
section 1.3) and has to be measured server-side.

### 4.3 Which branch is most likely

1. **Talk-power branch with a stale or mismatched book (most likely).**
   Bot 7 is in a moderated channel, and the server grants it speech
   through something the book did not update (group or channel-group
   change after enter view, or TS6 computing effective talk power
   differently from the `client_talk_power` it reports). This fits:
   per-bot difference (bot 5 on Sep 16, bot 7 today), constant from
   frame 1, and audible audio.
2. **A client-self flag reported as off by TS6** (hardware or away). This
   fits audible audio because the server does not enforce these flags.
   The same code path and server on Sep 16 did not trip it, so it needs
   a TS6 server change or a per-identity difference to explain the
   timing.
3. **Unmoderated channel with a negative book `talk_power`.** Unlikely,
   but cheap to rule out with the same read.

The panel's "muted" tag (`client_is_talker == 0`) is the normal state
for any client in an unmoderated channel, so it proves nothing, as the
brief says.

### 4.4 Cheapest decisive experiment (E5) and what the parallel run will show

Read-only, zero code: through the panel's WebQuery on Floki, run
`clientinfo clid=<bot 7>` and `channelinfo cid=<bot 7's channel>` while
the bot plays. Record `client_input_muted`, `client_output_muted`,
`client_input_hardware`, `client_output_hardware`, `client_away`,
`client_talk_power`, `client_is_talker`, and
`channel_needed_talk_power`.

- If a flag is off, that is the branch.
- If the channel is moderated and the server's `client_talk_power` is at
  or above the requirement, the book is stale (branch 1).
- If everything passes server-side, the book differs from the server.
  A later PR should log the `CanSendAudio` transitions and a one-shot
  dump of the own-client fields.

For the parallel live experiment:

- If "give talk power" returns 1538, the channel is not moderated, and
  the talk-power branch can only fail through a negative book value.
  Look at the flags instead.
- If granting `client_is_talker=1` makes the WARN stop, the server sent
  `notifyclientupdated client_is_talker=1`, which set
  `talk_power_granted` in the book and confirms branch 1.
- In either case, compare loop metrics against E2. Granting talk power
  changes server state as well as logging, so E2 is the cleaner test of
  logging cost.

To check drop or throttle directly: sample the server-side packet
counters for bot 7 and one listener (the `clientinfo` connection
fields, or a `tcpdump -c` on Floki's UDP 9987 filtered by the Contabo
source address) twice, 60 s apart, during play. Field names differ
between TS3 ServerQuery and TS6 WebQuery, so verify them on TS6. About
3,000 voice packets in from the bot should match about 3,000 out to the
listener. A shortfall on the listener side would be the first evidence
of server-side dropping.

## Appendix: how the counts were computed

All counts come from `jq` and short Python passes over the raw logs.
Only the JSON fields were used, never message text, except for the
muted WARN and for reproducing the brief's grep figures.

```bash
# brief-style per-minute figures (line counts)
grep -c underrun LOG; grep -c C_loop LOG
jq -r 'select(.stage=="connected_loop_stall")' LOG | grep -c stage

# real underrun events and full-buffer share
jq -r 'select(.stage=="frame_underrun")|.buffered_frames' LOG | awk '$1>=249' | wc -l

# muted WARN count and per-frame ratio
jq -r 'select(.message=="Sending audio while muted")|.timestamp' LOG | wc -l
jq -r 'select(.stage=="audio_send_summary")|.total_frames' LOG | tail -1

# voice-rt thread starts per second
jq -r 'select(.message=="pinned current thread to cpuset").timestamp[11:19]' LOG | uniq -c
```

The send-gap trace (section 1.3) uses consecutive muted-WARN
timestamps. Gap coverage merges `[t - elapsed, t]` intervals from
`connected_loop_stall` (`elapsed_ms`), `voice_poll_leg` (`total_us`),
and `frame_underrun` (`lateness_ms`) inside each gap of 100 ms or more.
Out-of-order lag is the file-order timestamp regression against the
running maximum. The attached logs are not committed. The manifest
notes the repo is public.
